# cognitive-load

## なぜこのスキルが必要で、どのような状態を目指すべきか

このスキルが必要な理由は、AI がチャットの文章を「上から順に読まれるもの」として書くからだ。チャット UI は画面を下端の入力欄に固定する。持ち主は応答を待つ間も次の指示を考えているので、視線は入力欄の近くにある。上に積まれた経過は読まれず、その中に埋もれた確認事項は見落とされる。文章は流れていくので、今何の話をしているかも残らない。スライドや図でも、AI は要素を 1 つずつ解釈して作るが、人間は画面全体を一度に見て、位置、大きさ、色の違いを言葉より先に意味として受け取る。見た目が送る意味は、AI が意図したかどうかに関係なく届き、読み解く手間がそのまま負荷になる。

このスキルが目指すべき状態は、持ち主が視線を動かさず、過去のやり取りを覚えておかずに次の指示を決められ、資料を見る人が見た目を読み解き直さずに中身を受け取れる状態である。

## チャットに書く

- 作業報告は、開始時の状態と完了時の状態だけを書く。経過も調べた結果も、次の指示を決める材料にならない。調べた結果は、それを使った成果物の中に置く。
- 並ぶ項目は箇条書きにし、話し言葉の文につながない。文に溶けた項目は、目で拾えない。
- 作業時間の目安は書かない。AI の見積もりは実際の速さと合わず、読む量だけが増える。
- リンクは、その事実を書いた語句に埋め込む。末尾にまとめた出典は、本文のどこに対応するかを探させる。
- 指示を受けたら、「本質は〜で合っていますか。であれば〜が良いと考えます」の形で目的を確かめ、より良い手段があれば推奨として添える。持ち主は目的が合っているかだけを判断すればよくなる。
- 確認事項は、あるときだけ、メッセージの末尾に書く。末尾が入力欄に最も近い。
- 確認事項は、それだけを読んで答えられる文にする。上の文を読み返させない。
- 構造を持つ説明や比較は、チャットに書かず HTML の資料にする。チャットは流れるので、構造を保てない。

## スライドや図を作る

人間の見方に沿わない見た目は、見る人に読み解き直させる。次の性質を前提に作る。

- 位置を量として読む。同じ高さや同じ列に並んだものは同じ軸の上にあると読み、そのまま比べる。比べる量は共通の軸の上の位置で見せたときに最も正確に読まれ、軸が別々だったり縦棒と横棒のように形が違ったりすると比べられない（[Cleveland と McGill の位置判断](https://info3312.infosci.cornell.edu/slides/04-graphical-perception.html)）。
- 近いもの、囲まれたもの、同じ色や形のものを 1 つのまとまりと見る（ゲシュタルトの近接、閉合、類同）。意図しない近さや揃いも、まとまりとして読まれる。
- 大きさや色の違いは、読む前に目に入り、意味があるものとして受け取られる（前注意特性）。意図のない違いは「なぜここだけ違うのか」という疑問になる。強調は周りが揃っているときにだけ効き、全部を強調すれば何も強調されない。
- 一度に頭に置けるのは 3〜5 個のまとまりまでだ（[Cowan 2001](https://www.cambridge.org/core/journals/behavioral-and-brain-sciences/article/magical-number-4-in-shortterm-memory-a-reconsideration-of-mental-storage-capacity/44023F1147D4A1D44BDC0AD226838496)）。要らない要素は、要る要素の置き場所を奪う。
- 図は関係を見せるが、何を言いたいかは見せない。図だけを見た人は、何も変わっていないと受け取るか、主張を自分で推測する。
- 話を聞きながら文字は読めない。話す内容がそのまま画面に書いてあると、聞き手は読むか聞くかを選び、画面と話し手を行き来して取りこぼす（[Mayer の redundancy と signaling](https://www.unh.edu/teaching-learning-resource-hub/sites/default/files/media/2023-06/itow-research-based-principles-for-designing-multimedia-instruction-mayer.pdf)）。説明に合わせて要素を順に出すと、視線が今の要素に早く向く（[東京理科大学 2026](https://www.tus.ac.jp/en/mediarelations/archive/20260709_1132.html)）。
- 言葉遣いから、資料と書き手の水準を判断する。その場の業界で使う語の代わりに平易すぎる言い換えを使うと、中身より先に幼さが目に入る。

## UI を作る

- 作り始める前に、ワイヤーフレームを見せて見た目を合意する。文章で説明された UI は、持ち主が頭の中で組み立て直すことになる。
- 作るたびに、AI slop と呼ばれる見た目の特徴を Web で調べ直し、作ったものと照らし合わせる。モデルが自然に選ぶ既定値がそのまま AI slop であり、何が既定値と見抜かれるかは月単位で変わる。

## 説明資料を作る

- 経緯を一切知らない人が、最初から最後まで読んで理解できるように書く。資料は完成品として読まれる。
- 作成の経緯、途中の状態、それまでの説明の訂正は書かない。読み手の理解に寄与しない。
- 数えただけの数は書かない。意味を持つ数だけを残す。
- 文字だけで説明せず、図表で示す。
- 未決事項や確認事項のページやセクションを作らない。書く必要があるものは、それが影響する箇所のすぐ横に注釈として書く。
- [GitBook](https://gitbook.com/docs/) 風にし、サイドバーの項目ごとに別のページにする。1 つのページをスクロールさせる形は、今どこを読んでいるかを持ち主に覚えさせる。
