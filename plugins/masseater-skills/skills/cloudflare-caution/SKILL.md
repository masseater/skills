# cloudflare-caution

- すべてのリクエストで結果が同一になる処理は実行しないこと。
- 実行時に処理が停止する仕組みをコードや設定に組み込むこと。
- コストは請求単位単位で見積もり、本番環境での利用状況を確認すること。

## なぜこのスキルが必要なのか、そしてどのような状態を実現すべきか

このスキルが必要な理由と、実現すべき状態について。Cloudflareは利用量に応じたきめ細かな単位で課金しており、支出に上限はない。単位あたりのコストが低いため、記述時に負担にならないが、すべてのビューで実行される処理や、ループ・リトライのバグについては、実行回数がそのまま請求額となる。

このスキルが実現すべき状態とは、設計段階で1回の訪問コストが決まることだ。バグやボットが想定を超えて発生した場合でも、コードや設定が請求額になる前にそれを阻止してくれる。

## 同じ結果が得られるものを事前構築すること

すべてのビューで同じものを再構築すれば、Workerの呼び出し回数、CPU時間、DB行数が訪問回数に比例して請求される。事前構築可能なものはすべて事前構築して提供すること。

- CSPノンスを使用するということは、リクエストごとにHTMLを構築することを意味する。公開静的ページではノンスに依存せず、インラインスクリプトを外部ファイルに移動し、すべてのページに共通するCSPを `_headers` でアタッチすること。`_headers` にページごとのハッシュ値を列挙すると、最終的にルールの上限（100）で破綻する。
- 静的アセットに一致するリクエストは、デフォルトで[Workerを呼び出さずに提供される](https://developers.cloudflare.com/workers/static-assets/)ため、請求されない。互換性フラグ `assets_navigation_prefers_asset_serving`（デフォルト、互換性日は 2025-04-01）が有効な場合、ナビゲーションのフォールバックでもWorkerは呼び出されない。
- `assets.run_worker_first` を、認証およびAPIパスのみを含む配列に絞り込む。これを `true` に設定すると、静的アセットへのすべてのリクエストがWorkerの請求対象にもなる。
- ビューアごとに変更される部分のみを動的にする。ページ全体を動的にしない。
- 動的データは、変更頻度に応じてCDNキャッシュ、Cache API、またはKVに格納する。すべてのリクエストでD1や外部APIを呼び出さない。
- クライアント側では、データが変更されていない間は再取得しない。TanStack Query を使用する場合は、`staleTime` を設定する。

## ランナウェイに対するブレーキ

- コードを実行するすべてのWorkerに、[Workers の制限のページ](https://developers.cloudflare.com/workers/platform/limits/) に従って `limits.cpu_ms`（Alchemyでは `limits.cpuMs`）を指定する。これは、単一の実行がランナウェイするのを防ぐ唯一の公式な手段である。既定値は30秒である。本番環境のCPU時間を測定し、p99ではなく観測した最大値をわずかに上回る値にする。p99を上限にすると、最も遅いリクエストを意図して失敗させることになるからである。この値を最大まで上げると、無限ループがそのまま請求対象となる。コードを持つWorkerやWebsiteに `limits.cpuMs` が無いと、mschのlintが落とす。
- 公開API、認証、および書き込みエンドポイントの前にレート制限を設ける。レート制限を設けない場合、ボットによるすべての大量アクセスが請求対象となる。
- ゾーンを所有するリポジトリではWAFのレート制限ルールを、所有していないリポジトリではWorkerの [Rate Limiting バインディング](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) を用いてレート制限を適用する。このバインディングはロケーションごとの近似値であり、制限を超えた場合でも停止しないことがある。正確な制限が必要な場合は、WAFのレート制限ルールまたはDurable Objectカウンターを使用する。
- キューコンシューマー、Durable Objectアラーム、およびリトライ処理を冪等にする。自身で再エンキューを行わないこと。
- 再エンキューおよびリトライの回数に上限を設ける。
- モデルの呼び出しは [AI Gateway](https://developers.cloudflare.com/ai-gateway/) を経由させ、ゲートウェイに [支出制限](https://developers.cloudflare.com/ai-gateway/features/spend-limits/) を設定する。Workers AIには独自の上限がない。ループする呼び出し元や、すべてのファイルを判定するジョブは、誰かが気づくまでニューロン単位で課金され続ける。その日の予算を使い切ると、ゲートウェイはウィンドウがリセットされるまで429を返す。同じリクエストでモデルを再び動かさないよう、ゲートウェイのキャッシュを有効にする。
- CIで、実行のたびにすべてのファイルへモデルを呼ばない。キャッシュに当たらないリクエストは実行ごとに課金されるので、費用はファイル数と実行回数の積で増える。変更された部分だけを問い、回答は実行をまたいで残るキャッシュに保存する。
- アカウントに [予算アラート](https://developers.cloudflare.com/billing/manage/optimize-costs/) を設定する。これは停止させるためのものではなく、早期に検知するためのものである。

## 書き込みおよび操作の削減

書き込みおよびリスト操作のコストは、読み取り操作よりも1〜3桁高い。

- D1およびDurable ObjectへのバッチKV書き込みおよび行書き込み
- 値が変更されていない場合は書き込みを行わない。
- すべてのリクエストでKVの `list()` を呼び出さない。キーで直接値を参照できるように設計する。
- Durable ObjectをWebSocket Hibernationおよびアラーム付きでスリープさせる。スリープ状態では、未使用であっても128 MB分の時間が請求される。
- `setTimeout` やアウトバウンド接続によって、Durable Objectをスリープさせない。
- Containersは、処理の有無にかかわらず、コンテナが稼働している間、インスタンスタイプのフルメモリおよびフルディスクを10 ms単位で課金する。本番環境で測定される最大メモリ容量に適合する最小のインスタンスタイプを使用し、`setInactivityTimeout` または `sleepAfter` のアイドル時間を、本番環境で測定されるコール間隔が許容する最短値に設定する。スケジュールに基づいて呼び出されるコンテナでは、すべての呼び出しでアイドル時間の全量が課金される。いかなるスペンドポリシーによっても、Containersを停止させることはできない。
- 書き込みや読み取り回数の多い小規模ファイルに対して、R2 Infrequent Accessを使用しない。操作ごとのコストがStandardよりも高くなる。

## ログとトレースの希釈

ログとトレースの両方をボリューム単位で請求する。

- Cloudflareにすべてのリクエストのログを保存し続けない。`head_sampling_rate` で必要な量のみをサンプリングする。
- 外部にのみ送信する場合は、`persist: false` を設定する。

## ログと利用状況を7日を超えて保持すること

Workers Logsは、Workers Paidであっても最大7日間までログを保持し、期間を延長する設定はない。データの用途に応じて、保存先を選択すること。

- MCPツールごとの呼び出し回数や所要時間など、カウントまたは合計する使用量を `writeDataPoint()` で Workers Analytics Engine に書き込む。その SQL API で集計でき、データを3か月間保持する。ログをパースして使用量を収集してはならない。それは、数万もの小さなファイルを読み込むことを意味するからだ。
- インシデント調査用の生ログを、`workers_trace_events` データセットに対する Logpush ジョブで R2 に送信する。失敗（`ok` 以外の `Outcome`）は完全な状態で保持し、残りはサンプリングした上で、遡って確認する期間の後に R2 のライフサイクルルールで削除する。
- Claude CodeのOpenTelemetryエクスポートでは、MCPツール名が`mcp_tool`として隠蔽されるため、サーバー側でのツールごとの利用状況を代替することはできない。

Logpushにはこうした落とし穴がある。

- このジョブは、`logpush` が `true` である Worker からのみログを受け取る。デプロイ後、API 経由ですべての Worker の `script-settings` を確認すること。Worker を作成するライブラリでは `logpush: false` を明示的に設定でき、これによりデフォルト設定よりも優先される。
- R2 の宛先には S3 互換キーが使用される。アクセスキー ID は API トークンの `id` であり、シークレットアクセスキーはトークン `value` の SHA-256 である。トークンのスコープはバケットに限定し、`Workers R2 Storage Bucket Item Write` のみを使用する。書き込みは読み取り権限なしで動作する。
- そのトークンに有効期限を設定してはならない。有効期限が切れると、実行中のジョブはエラーなく書き込みを停止する。トークン発行権限が既に付与されている箇所で発行し、デプロイ側にはキーのみを付与すること。
- 失敗し続けるジョブは無効化される。`failing_logpush_job_disabled_alert` の通知ポリシーを作成し、作成しないと、ログが届かなくなったことに誰も気づかない。
- Logpushは、ジョブごとに1分間に1つの小さなgzipファイルを書き出す。不完全なマルチパートアップロードを中断するライフサイクルルールと、有効期限ルールを追加する。
- ジョブを作成する際、Logpushは書き込みが可能かを確認するため、`00010101`フォルダ配下に`test.txt.gz`を書き込む。
- R2 REST API は、オブジェクトを解凍し、`content-type: application/json` を指定して返す。`response-content-type=application/octet-stream` を指定すること。そうしないと、レスポンスを JSON としてパースするクライアントは NDJSON で失敗する。
- 2026-11-19現在、Pipelines のデスティネーション（Iceberg テーブル）を持つ Logpush ジョブは、ダッシュボードからのみ作成可能である。

## 本番環境での見積もりと確認

推測ではなく実測に従う。

- 設計を決定する前に、想定される訪問回数に、1回あたりのWorker呼び出し数、行数、操作数、およびログ数を乗じて月間コストを見積もります。
- デプロイ後は、ダッシュボードの Billable Usage または GraphQL Analytics API で本番環境の利用状況を確認する。見積もりと乖離がある場合は、設計を見直す。
- 請求可能な使用量を毎日確認すること。請求額が0を超える日はすべて所見として扱い、プロダクト、次いでスクリプト、コンテナアプリケーション、またはモデルへと遡って追跡すること。
- `aiInferenceAdaptiveGroups` におけるモデルごとの Workers AI リクエストと、`aiGatewayRequestsAdaptiveGroups` におけるモデルごとの AI Gateway リクエストを比較する。推論リクエストはあるがゲートウェイリクエストがないモデルはゲートウェイを通らずに呼ばれているため、その支出に上限はない。
- 呼び出し元が自身のマシンで実行できる場合は、コンテナにモデルをホストしてはならない。コンテナは、次の呼び出しを待つ間、メモリ容量の全額を課金し続ける。

請求単位および単価は以下の通りである。2026-10-27に [Workers の料金ページ](https://developers.cloudflare.com/workers/platform/pricing/) およびその他の箇所で、Workers AIは2026-11-16に [Workers AI の料金ページ](https://developers.cloudflare.com/workers-ai/platform/pricing/) で、Containersは2026-11-17に Workers の料金ページで確認済みである。単価は変動するため、見積もりに使用する前に料金ページで確認すること。
