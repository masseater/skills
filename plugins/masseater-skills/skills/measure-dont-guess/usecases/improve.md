# 何かを改善する

1. 対象を、答えが数値か型付きの判定（はい・いいえ、複数のうちの 1 つ、スコア）になる 1 つの問いにする。変更で動きうる観点は [`dimensions`](../references/dimensions.md) から取る。
2. 受け入れ値を書き出し、再測定で使う条件と同じ条件で基準値を測定する。
3. 文章が明瞭に読めるか、ルールが守られているか、ページが読み手に負荷をかけていないかのように、対象が数値を持たない質であるときは、decision モデルへの問いとして書く。decision モデルは型付きの問いに答えるだけで書き換えず、候補ごと、ファイルごとに実行できるほど速く安い。信頼する前に、答えが分かっている入力で各問いを試す。
4. 候補は Claude が出し、decision モデルが選択、順位付け、却下をする。変更は 1 つずつ適用する。
5. 同じ方法で再測定する。受け入れ値を満たすなら変更を残し、満たさないなら元に戻す。ほかの観点も測定する。ある観点での向上は、別の観点を損なうことが多いためである。
6. 問いが信頼できると確かめられ、今後も質を保つ必要があるときは、`oxlint-plugin-decision` のルールにする。`decision-rules.ts` に `defineDecisionRule` で平易な英語のルールとして書くと、誰も覚えていなくても `vp check` が退行を検出する。

セッションが自分の変更について下す判定は、そのセッションの文脈で動く。decision モデルは、次の変更でも同じように実行し直せる測定器である。decision モデルは判定し、生成モデルは書く。答えの形と価格が違うので、それぞれ自分の種類の呼び出しに使い、入れ替えない。

パフォーマンスも同じループである。対象にスパンを置き、スパンが示すボトルネックに変更を適用し、同じ条件で再測定する。
