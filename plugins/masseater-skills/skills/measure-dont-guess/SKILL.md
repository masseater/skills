# measure-dont-guess

- 測定を行う前に、仮説とそれを受け入れる値を記述する
- 本番環境、または本番環境と同じ条件で測定する
- 未測定の主張が推測であることを明示する
- 測定できない場合は推測で進めず、何が不足しているかをユーザーに伝えること
- 測定前に、判断が依存する観点を列挙し、それぞれを測定するか、測定値で除外する
- 何かを改善するときは、対象を測定に落とし（数値にならない質は decisionモデルへの問いにする）、変更は1つずつ行い、再測定して、変更を残すか元に戻す

## なぜこのスキルが必要なのか、そしてどのような状態を実現すべきか

推測は測定よりも早く答えを出せる上、通常は妥当に見えるため、このスキルが必要となる。推測に基づいて行った変更では、それが間違っていることに気づくための材料が残らない。測定もまた、作成者が想定した観点しか覆わない。少数の観点を測定した判断は、すべての観点に基づく判断と同じくらい妥当に見える。メモリやストレージのように誰も想定しなかった観点は結果に現れず、後になって失敗する。

このスキルが実現すべき状態とは、あらゆる判断が誰でも再現可能な根拠に基づいていることである。判断を変えうるあらゆる観点が、測定されているか、測定値によって除外されていることである。

## 本番環境での測定

判断の根拠となる測定は、本番環境で行われる。ローカル環境とテスト環境ではデータ規模や外部サービスが異なり、本番環境とは正反対の結論に至ることがある。

- 本番環境で測定できない場合は、ステージング環境を構築し、そこで測定を行う。
- コード、構成、インフラストラクチャ、データの規模や形態、および外部サービスにおいて、ステージングを本番環境と同等にする。
- ローカル環境およびテスト環境における測定は、測定メカニズムが動作することを確認するためにのみ使用する。

## 測定値の記録

- 変更の根拠となる測定値については、条件、コマンド、および結果をコミットメッセージに記述する。
- 不都合な結果が出た場合は、そのまま報告し、仮説を再検討する。
