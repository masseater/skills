# Feature-Sliced Design

アプリは Feature-Sliced Design v2.1 に準拠する。ここでは、「ページ優先」の既定に代わる 2 つのルールを適用する。コードを多くのスライスに分割し、スライスのファイルをすべてそのスライスの中に置く。Steiger が `@r_masseater/msch/lint` の `fsdRules` でスライスの境界を検査し、msch の `colocated-test` 検査がテストの置き場所を検査する。feature-sliced-design スキルの「pages first」と「再利用されるまで切り出さない」は、ここでは従わない。

## なぜ

画面のすべてのモデル、フック、コンポーネントを抱えるページスライスには、内部に境界がない。どのファイルも他のファイルをインポートできるため、ある操作の変更がスライス全体に広がり、読み手はどのファイルがまとまっているかを判別できなくなる。パブリック API を持つスライスはこれらのまとまりを見えるようにし、リンターがそれらを分けたまま保つ。ページ用のテストを `app/` に置く、1 ページ用のスタイルをグローバルなスタイルシートに置くなど、スライスから離れたコードは、スライスを変更または削除したときに見落とされる。

## スライス

- 利用者の操作ごとに `features/<verb>-<object>` スライスを作り、複数のスライスが使うビジネスオブジェクトごとに `entities/<noun>` スライスを作る。今は 1 ページしか使っていなくても分ける。このため `fsd/insignificant-slice` は無効にしている。
- `edit-song` と `edit-video` のように複数の機能が単語を共有する場合は、`edit-catalog` のように 1 つのスライスに統合する。`fsd/repetitive-naming` が重複した単語を報告する。
- `pages/<route>` には、画面の組み立てと、他のスライスが必要としないコードだけを置く。インタビュー後のレポートなど、同じルートで別の画面と入れ替わる画面は独立したページとし、`app` がどちらを出すかを選ぶ。
- アトムのヘルパー、ストレージ、テレメトリ、テキストのユーティリティなど、ビジネスルールを含まないコードは `shared/<segment>` に置く。
- `widgets/<name>` は、ナビゲーションやフィルターを備えたページの外枠のように、複数のページが複数の機能から組み立てるブロックにだけ使う。
- スライス内では、セグメント `ui`、`model`、`api`、`lib`、`config` を使う。セグメントは用途で名付ける。`hooks`、`types`、`components` はセグメントではない。セグメントが大きくなったら、中にフォルダを作ってよい。

## パブリック API とインポート

- 各スライスが公開するのは、`index.ts`、サーバー上でだけ動くコード用の `index.server.ts`、テストだけが使うヘルパー用の `index.test.support.ts` だけである。別のスライスは、これらのファイルを通じてだけインポートする。`shared/ui` と `shared/lib` はファイルパスでインポートしてよい。`api`、`config`、`db` など、そのほかの `shared` のセグメントにはインデックスが必要である。
- スライス内では、同じディレクトリのファイルを `./name.ts` で、それ以外のファイルを `#/` エイリアスでインポートする。親パス（`../`）は使えない。
- パブリック API で別のスライスを再エクスポートしない。インポートする側が、そのスライスを直接使う。
- 下位のレイヤーからだけインポートする。同じレイヤーの 2 つのスライスが互いを必要とする場合は、共有する部分をエンティティか `shared` に下ろすか、ページから渡す。エンティティ同士では、使われる側のスライスが `@x/<使う側>.ts` を公開し、使う側はそのファイルだけをインポートする。
- Vite プラグイン、ワーカー、スクリプトなど、`src/` の外のコードはレイヤーに含まれない。スライスのパブリック API が UI まで取り込んでしまう場合は、`src/` の中のモジュールをファイルパスでインポートしてよい。

## コロケーション

- スライスの UI、ロジック、スタイル、テスト、テストのヘルパーは、そのスライスの中に置く。
- `foo.test.ts` を `foo.ts` の隣に置き、`./foo.ts` としてインポートする。テストのヘルパーはテストの隣に `foo.test.support.ts` として置く。`__tests__`、`tests`、`test` のディレクトリは作らない。
- ツールレジストリを通した MCP ツールのテストや、アプリのプロバイダーを使った画面のテストなど、組み立てたアプリを動かすテストは、それを組み立てるモジュールの隣の `app/` に置く。
- `app/styles.css` には、グローバルなスタイルとテーマのインポートだけを置く。1 つのスライスのスタイルは、そのスライスの中に置く。

## 列挙で合わせない

規約に沿わない置き方を、設定ファイルにファイルやディレクトリを 1 つずつ書き並べて検査に通してはならない。fallow の `entryPoints` にスクリプトを 1 本ずつ書く、lint の `overrides` や `ignore` にファイルを書き並べる、Steiger の `paths` にワークスペースを 1 つずつ書く、といった設定がこれに当たる。並べた一覧は違反を隠すだけでなく、ファイルを足すたびに書き足す必要があり、消したファイルの名前も残り続ける。

- ツールが規約から対象を見つけられるようにする。入口は `package.json` の `bin`、`exports`、`imports` に宣言し、テストは `*.test.ts` の名前で、スライスは FSD のレイヤーで見つけさせる。設定にはそうした規約を表す glob だけを書く。
- 一覧が要るように見えたら、置き方が規約から外れている。コードをスライスへ移すか、入口を `package.json` に宣言して一覧を消す。ツールが規約を読めないなら、ツールの側に規約から対象を導く処理を足す。
- 例外は、publint と attw を fallow の `ignoreDependencies` に書く場合のように、ツールが使われ方を原理的に辿れない依存だけである。コードのファイルやディレクトリは例外にしない。
