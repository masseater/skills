# CI

- ワークフローのステップについては、masseater/typescript-template の `.github/actions/` にある複合アクション（verify, autofix, update-branches, credentials, ci-telemetry）を `masseater/typescript-template/.github/actions/<名前>@<sha>` として参照すること。ステップが各リポジトリにコピーされる場合、すべての修正は各リポジトリの書き換えを意味する。renovate は sha を bump する。
- main への push で動く job は、後の push が同じ仕事をやり直すので、最新のコミットの分だけ動けばよい。こうした job には job の `concurrency` に `cancel-in-progress: true` を付け、新しい push が古い run を取り消すようにする。ワークフロー全体の `concurrency` で取り消すと走っているデプロイまで止まるので、job ごとに付ける。デプロイとリリースの job は途中で止めると半端な状態が残るので `cancel-in-progress` を付けず、待っている古い run だけを新しい run に置き換えさせる。
- リポジトリ固有のツール（go、weaver、apt の依存関係など）をそのリポジトリの `.github/actions/setup` に配置し、ジョブからは `$/.github/actions/setup` として呼び出すこと。fu4 は `$/` を受け付けるので、これに linter の設定は要らない。
- credentials アクションは、credentials.masseater.dev から Cloudflare と Claude のトークンを受け取る。これらを GitHub Secrets に配置しないこと。
- ボットがブランチにプッシュするワークフロー（autofix, update-branches）は、ブローカーが発行した GitHub App トークンでプッシュする。`GITHUB_TOKEN` でプッシュした場合、`pull_request` の `up-to-date` が承認待ちを停止し（action_required）、PR はマージされないままとなる。ブローカーはワークフローのファイル名で権限を付与するため、ボットのワークフローを追加する際は、masseater.dev の `credential-grants.ts` にある `WORKFLOW_GITHUB_GRANTS` にも追加すること。
- `update-branches.yml` はマージキューである。GitHub のマージキューは、組織が所有するリポジトリでのみ動作するためだ。ドラフト以外のすべてのプルリクエストがキューに入る。プルリクエストを開いたら自動マージを有効にする。プルリクエストは、GitHub がマージ可能（`CLEAN`、`UNSTABLE`、または `HAS_HOOKS`：競合がなく、必要なチェックがすべてパスされている状態）であると報告し、かつその配下にオープンなプルリクエストが存在しない時点で準備完了となる。他方のプルリクエストが自分のヘッドコミットを含むか、自分のベースが他方のブランチであるとき、他方は自分より下にある。このキューは、準備完了したプルリクエストを、開かれた順にスクワッシュでマージし、それらを順次処理した後、一覧を読み直し、ベースブランチがマージ済みになったプルリクエストのベースをデフォルトブランチに付け替え、準備完了になったものをマージする。何もマージされなくなるまで繰り返す。ブランチを最新の状態に更新しないため、リポジトリのルールセットで最新のブランチを必須としてはならない（`strictRequiredStatusChecksPolicy: false`）。競合または必要なチェックの失敗が発生した場合、ヘッドコミットごとに 1 回だけコメントし、それ以外は何もしない。デフォルトブランチで `verify` が赤の間は、ボットが開いたプルリクエストだけが待つ。キューは `workflow_dispatch` を通じて再起動される。これは、ブローカーが `pull_request_target` または `workflow_run` 用のトークンを発行しないためである：`up-to-date.yml` の `wake` ジョブ（または必要なチェックがないリポジトリの `queue-wake.yml`）、デフォルトブランチへのすべてのプッシュ、および1時間ごとのスケジュールに基づいて行われる。実行中のキューを取り消さない。`concurrency` が実行を順番待ちにする。キューの使用方法については、SKILL.md の「PR とマージ」を参照すること。
- `up-to-date.yml` に `concurrency` を記述してはならない。必要なチェックの結果としてキャンセルされた実行が残ると、GitHub はそれをチェックの結果として扱い、プルリクエストはチェックが 緑のままブロックされたままになり、キューは永遠に待機し続ける (masseater.dev #1435)。
