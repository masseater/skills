# land-parallel-prs

複数のスレッドが同じリポジトリに PR を出していても、verify のやり直しと衝突の解き直しを繰り返さずに main へ入れる。`vp run verify` は時間がかかり、main がその間に進むと、取り込み直してまた最初から回すことになる。

1. 着手する前に、開いている PR を `gh api repos/<owner>/<repo>/pulls` で一覧し、触るファイルが重なる PR と、その PR に依存する作業を洗い出す。
2. 別のプルリクエストに依存するプルリクエストをその上に配置する。そのブランチを別のプルリクエストのブランチから切り、待たずに開く。キューは単独でスタックを検出し、下から上へとマージを行い、下のプルリクエストがマージされた後、上のプルリクエストのベースを `main` に付け替える。他のプルリクエストに依存しないプルリクエストは `main` からブランチを切る。どのプルリクエストも自動マージを有効にし、`main` を手動で上のプルリクエストにマージしてはならない。
3. 大規模な変更はまずマージすること。多くのファイルを移動または名称変更するプルリクエストは、マージが後になるほど競合が増え、それを解決した人が未知の箇所を壊してしまう可能性がある。まずは大規模なプルリクエストを開くこと。キューは、開かれた順に準備完了のプルリクエストをマージしていく。それを開いたスレッドが、キューからコメントを受けた際に競合を解決する。
4. 衝突は、実際に取り込む前に `git merge-tree --write-tree --name-only <自分の HEAD> origin/<ブランチ>` で確かめる。作業ツリーに触らずに、衝突するファイルが分かる。
5. 競合しないプルリクエストを一つのブランチにまとめないこと。キューでは、同一ラン内でそれらを順次マージする。また、release-pleaseプルリクエストもまとめないこと。release-pleaseは、自身のプルリクエストがマージされる際にリリースを作成するためである。
6. main の CI が積み上がらないように、job の `concurrency` は SKILL.md の決まりに従い、後の push がやり直す job は古い run を取り消させる。
