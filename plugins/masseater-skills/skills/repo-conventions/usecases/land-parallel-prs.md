# land-parallel-prs

複数のスレッドが同じリポジトリに PR を出していても、verify のやり直しと衝突の解き直しを繰り返さずに main へ入れる。`vp run verify` は時間がかかり、main がその間に進むと、取り込み直してまた最初から回すことになる。

1. 着手する前に、開いている PR を `gh api repos/<owner>/<repo>/pulls` で一覧し、触るファイルが重なる PR と、その PR に依存する作業を洗い出す。
2. 別のプルリクエストに依存するプルリクエストは、依存先のブランチを base にして積む。依存のないプルリクエストは main を base にする。下位のプルリクエストがマージされたら、main を上位のプルリクエストにマージし、そのベースを main に変更して自動マージを有効にする。マージはスクワッシュされるため、スタックされたプルリクエストのベースは単独では追従しない。
3. 大規模な変更は先にマージすること。ファイルの移動や名称変更が多いプルリクエストは、後からマージするほど競合が増え、解決者が内容を知らずに壊してしまう恐れがある。大規模なプルリクエストはまず自動マージを有効にすること。キューは自動マージが有効な順にプルリクエストをマージするためだ。作成したスレッドは、キューによって外された場合に競合を解消する。
4. 衝突は、実際に取り込む前に `git merge-tree --write-tree --name-only <自分の HEAD> origin/<ブランチ>` で確かめる。作業ツリーに触らずに、衝突するファイルが分かる。
5. 競合しないプルリクエストを多数入れる場合は、順次1つのブランチにマージし、一度だけ verify を通し、そのブランチのプルリクエストの自動マージを有効にした上で、マージ済みのプルリクエストをリンク付きでクローズする。release-please のプルリクエストはバンドルせず、そのままキューに回すこととする。というのも、release-please は自身のプルリクエストがマージされた際にリリースを作成するからだ。
6. main の CI が積み上がらないように、job の `concurrency` は SKILL.md の決まりに従い、後の push がやり直す job は古い run を取り消させる。
