# land-parallel-prs

複数のスレッドが同じリポジトリに PR を出していても、verify のやり直しと衝突の解き直しを繰り返さずに main へ入れる。`vp run verify` は時間がかかり、main がその間に進むと、取り込み直してまた最初から回すことになる。

1. 着手する前に、開いている PR を `gh api repos/<owner>/<repo>/pulls` で一覧し、触るファイルが重なる PR と、その PR に依存する作業を洗い出す。
2. 依存のある PR は、依存先の PR のブランチを base にして積む。依存のない PR は main を base にする。下の PR がマージされたら、上の PR に main を取り込み、base を main に付け替える。squash でマージするので、積んだ PR の base は自動では追従しない。
3. 大きい変更から先に入れる。ファイルの移動や名前の変更を多く含む PR は、後から入れるほど衝突が増え、解く側が中身を知らないと壊しやすい。大きい PR は書いたスレッドが main の上で衝突を解いてマージし、小さい PR がその後に main を取り込む。
4. 衝突は、実際に取り込む前に `git merge-tree --write-tree --name-only <自分の HEAD> origin/<ブランチ>` で確かめる。作業ツリーに触らずに、衝突するファイルが分かる。
5. 衝突しない PR を何本もマージするときは、1 本のブランチに順に取り込み、verify を 1 回だけ通してから squash でマージし、取り込んだ PR にはそのマージへのリンクを残して閉じる。release-please の PR はまとめず、それだけで最後にマージする。release-please は自分の PR がマージされたことでリリースを作るからである。
6. main を取り込み直したあとは、verify を最初から回さない。衝突が無く、vp のキャッシュが効く範囲の差分だけを確かめてマージする。
7. ワークフローの `concurrency` に `queue: max` を付けない。古い run から 1 本ずつ通すので、push が続くと run が何時間も積み上がる。どのジョブも最新のコミットかを確かめてから動く作りにして、新しい run が古い待ちを置き換えるようにする。
