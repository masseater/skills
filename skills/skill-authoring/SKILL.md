# skill-authoring

skill は https://agentskills.io/specification が定義するもので、frontmatter、ディレクトリ構成、ファイル参照はこの仕様に従う。読むのは Claude なので、文章は https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices と、そこから辿れる読み手の model 向けのガイドの通りに書く。「書きぶり」はその要点である。文章は writing に、ユーザーの読み方と考え方の前提は humanity-and-humanness に従う。

## この skill が必要な理由と達成したい状態

この skill が必要な理由は、skill を書く AI がユーザーの判断を持っていないことにある。ユーザーが skill を書かせるのは、自分の判断を一度書いておけば、自分がいない場でもその判断で AI が動くようにするためである。ところが書く AI は判断を持たず、足りない部分を自分の知識や一般的な文書の型で埋める。埋めた記述もユーザーの判断と同じ顔で skill に残り、読んだ AI はそれをユーザーの判断として実行する。これを防ぐにはユーザーが全行を自分の判断と照らして弾くしかなく、それでは自分で書くのと変わらない。

この skill で達成したい状態は、skill がユーザーの判断だけでできていることである。

## 必要な理由と達成したい状態のセクション

規則が当てはまらない場面でモデルがそこから判断できるよう、本文には「この skill が必要な理由と達成したい状態」のセクションを 1 つ置き、手順や規則と分ける。どちらの文かを読み手に推し量らせないよう、中は「この skill が必要な理由は」「この skill で達成したい状態は」で書き出す段落を 1 つずつにする。この skill が何をするかは本文の規則そのものなので、このセクションには書かない。

- 必要な理由には、何が困るかだけでなく、それがなぜ起きるかの仕組みを書く。仕組みが書けていれば、規則が想定していない場面でも、同じ仕組みが働くかで判断できる。
- 達成したい状態には、skill に従い続けた先の状態を、手段に縛られない抽象的な形で書く。手順や具体的な基準は規則に任せる。

2 つが同じことの裏返しになったら、困りごとの解像度が足りない。症状だけを書くと、達成したい状態はその否定にしかならない。仕組みまで書けない skill は、まだ作る段階にない。

## 何を書くか

本文に書くのは、ユーザーが依頼と指摘で示した判断と、必要な理由と達成したい状態から導けることだけである。判断はユーザーのものであり、それをどう文章にするかはあなたが責任を持つ。

ユーザーは自分の判断をすべて言語化できているわけではないので、判断を尋ねるだけでは出てこない。たたき台を書いて見せ、その反応から判断を読み取る。ラバーダックの相手になるのであって、全部を自分で決めるのでも、全部を尋ねるのでもない。skill の必要な理由や達成したい状態を左右する判断は、たたき台に埋め込まず、選択肢と自分の推奨を示してユーザーに決めさせる。

ユーザーが決めていないところを、自分の知識や文書の一般的な型で埋めない。埋めがちなのは、頼まれていない前提、注意、補足の節と、念押しと、書き手にしか通じない言い回しである。判断を変えない文、ほかの場所の言い直し、言われなくてもモデルがやることは消す。迷ったら消す。

- 他の skill に委ねるときは skill 名だけを書き、中身は言い直さない。
- 読まれなければどれだけ整備しても意味がないので、`references/` のファイルに送るときは、関係するセクションの先頭に「[`name`](references/name.md) も読むこと」と書き、「〜は name にある」「〜のときだけ読む」のように読まなくてもよいと思わせる文脈は残さない。コンテキストが膨れても、これは不要だったと読んだ後に判断できればよい。
- 型、README、設定のような構造的な情報源は指し示し、写さない。繰り返す指示は文を足さずに lint、メタデータ、実行時の検査、スクリプトにする。poteto-principles の encode-lessons-in-structure に従う。
- 繰り返し踏むのに skill になっていない手順があれば、新しい skill を提案する。

## 書きぶり

- モデルは理由から、書いていない場面にも規則を広げて当てはめるので、規則には理由を一文添える。理由がなくても読み違えようのない規則には付けない。
- 「〜しない」で終えず、代わりに何をするかを書く。避けてほしい形は「汎用的な見た目を避ける」のような一般論にせず、具体的に名指しする。
- 出力の形を決めたいときは、文で説明するより良い例を示す。
- モデルは自分で考えて確かめ、指示すると過剰になるので、「よく考えてから」「最終確認をする」「見直してから答える」のように思考や検証の量を増やす指示は書かない。確かめ方を決めたいときは、量ではなく方法を書く。poteto-principles の prove-it-works にある「代わりのものでなく実物を見る」がその形である。推論を書き出させる指示は拒否されうるので、要るなら結果の短い説明を求める。
- いまのモデルは指示に過敏に反応するので、徹底させるための強い言い回しや強調を足さない。

## 直すとき

本文は必要な理由と達成したい状態から導いた結果であり、依頼を受けた順に足した履歴ではない。指摘を受けたら、指摘された一文ではなく、ユーザーがなぜそこを指摘したのかから判断を読み取る。直すときは poteto-principles の redesign-from-first-principles に従う。まず必要な理由と達成したい状態のどちらかが変わるのか、既存の規則のどれかが足りないのかを決め、本文全体をそこから導き直す。skill でよく起きる継ぎ足しは、指摘された一文を末尾に足すことと、見出しや箇条書きを一行増やして別項にすることである。読み手が覚えた構成を無駄に崩さないよう、導き直した結果が今の本文と同じ部分は書き換えない。

## frontmatter

- `name` はディレクトリ名と同じにする。本文の最初の見出しも同じ名前にする。
- `description` には何をするかと、いつ使うかを書く。使う場面の語を入れる。
- `license` は書かない。LICENSE ファイルも作らない。
- `metadata.derived-from` には、この skill の元になった skill の URL だけを書く。元になった skill とは、それを取り込んでこの skill を作ったもので、取り込んだ後に書き直していても元である。GitHub の URL はコミットを指定した permalink にする。元の URL、作者、バージョンは本文と `references/` に書かない。書くときに読んだ資料や、本文で根拠として引く資料は元ではないので、使う箇所の本文にリンクを書く。

`metadata` の値は文字列だけなので、複数の URL は空白区切りの 1 つの文字列にする。

```yaml
metadata:
  derived-from: >-
    https://github.com/<owner>/<repo>/blob/<commit>/path/SKILL.md
    https://github.com/<owner>/<repo>/tree/<commit>/path/another-skill
```

## 手順

1. skills CLI の `skills init <name>` で `SKILL.md` を作る。複数のリポジトリで使う skill は masseater/skills の `skills/` に置く。ここに置いた skill は Claude Code プラグイン `masseater-skills` にも入る。
2. 検証する。`skills-ref validate <dir>` を通し、frontmatter の規則を満たすこと、参照するファイルと、名前で委ねた skill が存在することを確かめる。
3. 構造的な内容ならテストケースを書く。主観的な内容なら書かない。
4. リポジトリの手順で PR を出す。

返答には、skill の要約、主な設計判断、検証の結果を書く。
