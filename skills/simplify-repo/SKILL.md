# simplify-repo

## この skill が必要な理由と達成したい状態

この skill が必要な理由は、リポジトリでは足すことには理由があっても、削ることには理由が要ることにある。機能も文書も抽象化も、足した時点ではそれぞれ正しい。だが残す側に立つ仕組みが無ければ、全体は増える一方になる。困るのは量そのものより、古くなった記述が現行の事実の顔で残ることである。エージェントは文書を現在の真実として読むため、陳腐化した一文は置いてあるだけでは済まず、作業を誤らせる。さらに、削る基準が共有されていなければ、単純化は好みの書き換え合戦になり、削るたびに別の複雑さが入る。

この skill で達成したい状態は、リポジトリに残っているものがすべて、振る舞いか誰かの判断を変えている状態である。機械が検出できるものは機械が検出し続け、文書にはコードより長持ちする判断だけが残る。単純化の前後で検証は同じ基準で通り続け、基準を緩めて通した箇所は無い。

## 規則

- 削る候補は機械に出させる。未使用のコードと重複は fallow のような検出を先に回し、出力されたものから手を付ける。人の勘で探し始めると、使われているものを壊すか、好みの書き換えに逸れる
- 検査や上限に当たったら、上限を上げるのではなく中身を軽くする。基準を緩めるのは単純化ではなく先送りで、負債が検出できない形に変わるだけである
- 文書には判断だけを残す。利用箇所、ファイルの一覧、実装の写しは、書いた瞬間から古くなり始める。コードと仕組みの重複の検出はツールに任せ、文書で二重に持たない
- 削る変更に、振る舞いを変える変更を混ぜない。PR は意味の単位で切り、検証が落ちたら削った分だけを疑える形にする
- 残すか迷ったものは「無くなると誰のどの判断が変わるか」で決める。答えが出ないものは削る側に倒す。必要になれば履歴から戻せる
- 効果の判断が要る場面では measure-dont-guess に従う。作業の進め方と検証は repo-conventions に従う
