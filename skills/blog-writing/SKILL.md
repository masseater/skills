# blog-writing

masseater の名前で出す記事を書く、直すときの規則である。

- 書く前に、6 つの種類のどれかを決める
- 全種類に共通の規則と、種類ごとの書き方の両方に従う
- 文章の一般的な規範は writing に、読み手の前提は humanity-and-humanness に従う

## この skill が必要な理由と達成したい状態

この skill が必要な理由は、AI が記事を、誰が何のために読むかからではなく、学習したそれらしい記事の形から組み立てることにある。そのため自分向けのメモに読者向けの前置きと正当化が付き、個人の主張を吐き出すポエムに反論への応答とデータの表が付き、寄稿レベルの記事には「〜から読み取れる」のような予告文や、同じ主張を言い換えただけの文が積み上がる。モデルを替えても同じ癖が出るので、本人は同じ指摘を記事ごとに繰り返すことになる。

この skill で達成したい状態は、本人の頭にある考えや調べた事実が、その記事の種類に合った形で、本人が直さずに出せる文章になっていることである。

## 種類

次から 1 つを選ぶ。依頼の言葉から決まらないときは、たたき台を書く前に本人に確かめる。種類を取り違えると、構成から書き直しになるためである。

- **調査メモ**：自分向けに調べた事実の記録。前置きと正当化を書かない
- **ポエム**：個人の主張を一人称の実感で吐き出す文章。論証しない
- **論説**：外部の人に読んでもらう寄稿レベルの記事。根拠を置き、読み手の疑問をつなぎながら主張へ進む
- **技術記事**：リポジトリ、ライブラリ、ツールの紹介と解説。対象が軸で、独自の主張を足さない
- **scrap**：外部の記事や事実へのリンクに、要約を 1、2 文添えたもの
- **教えてClaude**：本人が素朴な疑問を Claude と壁打ちした会話を、軽く整えてそのまま載せたもの

## 伝えたいことから書く

書く前に、記事全体で伝えたいことと、各段落で伝えたいことを決める。文はそれを読み手に伝えるために置き、伝えたいことに寄与しない文は書かない。AI は文の言い回しや個々の規則への適合を部分ごとに直しがちで、そうして直した文章は、一文ずつは規則に合っていても、段落が何を伝えたいのかが分からなくなる。

- 段落ごとに、伝えたいことを一文で言えるかを確かめてから書く
- 事例や数字は、伝えたいことの根拠として置く。事例から書き始めて、伝えたいことを読み手に推し量らせない
- 指摘を受けて直すときも、その文だけを差し替えず、段落の伝えたいことから文を組み立て直す
- 下の規則と [`ai-style`](references/ai-style.md) は、組み立てた文章を確かめるためのもので、規則に合わせて文を差し替えるためのものではない

## 人間の認知に合わせた構造

記事もメモも人間が読むものなので、どの種類も見出しと表を主にして構造化する。人間は AI と違い、全文を一度に読み込んでから処理することができない。上から小分けにした文章を読み取り、解釈し、次の文章へのフックを頭の中で組み立てながら読む。文章を書き連ねるだけでは、この組み立てが追いつかず、読んでも頭に残らない。

- 見出しで全体の地図を先に渡す。見出しは地図に要る分だけ付け、段落ごとに付けない
- 比べる項目は表にする
- 箇条書きは並列の項目にだけ使い、本文の 15% 以内に収める。masseater.dev の verify に入っている yomiyasu の lint が、それを超えると落とすためである
- 一つの段落には一つの主張だけを置き、次の段落へのフックを残す
- 図、表、コードのように文章でなくても伝わる方法があれば、それを使う

## タイトルと見出し

タイトルは、何の記事かが分かる最短の名詞句にする。「typescript-template の中身（2026年10月24日時点）」のように書き、「: Cloudflare で動く TypeScript アプリを検査と CI がそろった状態から始める」のような副題で内容の説明を足さない。説明は description と本文の冒頭に任せる。時点に依存する記事は「（YYYY年M月D日時点）」を残す。

見出しも同じく短くし、修飾や補足を重ねない。

## 全種類に共通の規則

[`ai-style`](references/ai-style.md) も読むこと。

- 依頼の軸から外れた独自の主張を足さない。記事の軸は本人の言葉で確かめ、自分の要約に置き換えない
- 本人の言葉は言い換えない。「複利」と言われたら「複利」と書き、借金や利払いのような比喩に広げない
- EOL、責任共有モデル、ペネトレーションテストのような英語の用語は、そのまま書く。平易な日本語に置き換えると、読み手には別物に見えるためである
- 造語的な圧縮表現を作らず、通常の業務用語で書く。「止めた」ではなく「停止した」、「決める」ではなく「決断する」と書く
- 出典は、その事実を書いた箇所に `[^codmon-retrospective]` のような名前のラベルの脚注で付ける。番号は描画時に出現順で自動で振られ、末尾の一覧へもまとまるので、番号も一覧も手で書かない
- 出典と、読者が辿る先のリンクを分ける。根拠を示す出典は脚注にし、紹介するツールの公式サイトや関連する記事のように読者に開いてほしい先は、本文の語に `[文言](URL)` で埋め込む
- 事例を並べるだけの文は書かず、まとめている記事へのリンクにする
- コードを読めば分かる設定値（プラグイン名、禁止ライブラリ、タスク一覧など）を並べない。仕組みと意図だけを書く
- 記事の末尾に、読者向けの始め方、次にやること、行動の呼びかけを書かない。骨子の段階でも入れない
- 字数の目安のように、制約として働きうる事項を骨子にも本文にも書かない
- 骨子や本文に、書き手の解釈や確認事項の注記を書かない。「CVA は CVE の誤記と解釈した」のような断りは、本人への返信で聞く
