# project-checklist

新しいプロジェクトの始めと大きな変更の前に、設計をユーザーが過去に下した判断と突き合わせるための一覧である。

- 設計を決める前に、各項目を設計の実物（構成、`alchemy.run.ts`、ワークフロー）と照らす

## この skill が必要な理由と達成したい状態

この skill が必要な理由は、設計の判断が、それを決めたセッションにしか残らないことにある。新しいプロジェクトを始める AI は、テンプレートの既定の形と一般的な作り方から設計する。テンプレートの Web アプリはリクエストごとに SSR する Worker なので、公開ページもそのまま SSR で作られる。ユーザーが前に「公開ページは静的に」と決めていても、その判断は今のセッションに無い。しかもこうした誤りは動いて見え、テストも verify も通るので、ユーザーが気づくまで残る。こうして同じ誤りがプロジェクトごとに作られ、ユーザーは毎回同じ指摘をすることになる。

この skill で達成したい状態は、ユーザーが一度下した設計の判断が、どのプロジェクトでも最初の設計から守られていることである。

## ページの配り方を方式から選ぶ

ページの配り方は、静的か動的かの二択ではない。中身が誰に対して、いつ変わるかで、方式が決まる。方式の分け方と向き不向きは web.dev の [Rendering on the Web](https://web.dev/articles/rendering-on-the-web) と patterns.dev の [rendering patterns](https://www.patterns.dev/react/) に従う。Cloudflare では方式ごとに、Worker がリクエストのたびに動くかどうかが決まり、それがそのまま費用になる。

- 見本は masseater/typescript-template の `apps/lp` で、作り方はそのリポジトリの AGENTS.md の「公開の静的ページ」にある。静的レンダリングを選んだページは同じ形で作る
- プリレンダーした HTML でも、Worker の SSR を通して返すなら静的レンダリングではない
- CSP の nonce やテンプレートの既定の形は、方式を選ぶ理由にならない
- 1 つのサイトの中でも、ページごとに方式を選ぶ。ページ全体を、いちばん動的な部分に合わせない

### 方式を選ぶ

ページごとに、HTML の中身を決めている入力を挙げ、それが誰に対していつ変わるかで次の表から選ぶ。

| 中身の変わり方 | 方式 | Cloudflare での配り方 |
| --- | --- | --- |
| 全員に同じで、デプロイのときだけ変わる | 静的レンダリング | 静的アセット。Worker は動かない |
| 全員に同じで、時間やイベントで変わる | 変わったときに再ビルドして静的アセットを差し替える。star の数のように頻繁に変わる部分だけを API で取る | Workers で ISR をすると、キャッシュから返すときも Worker が動く |
| 閲覧者ごと、リクエストごとに変わる（ログイン状態、検索結果、ライブの値） | SSR。遅いデータがあれば streaming SSR | Worker が毎回動く。変わる部分だけに限る |
| ほとんどが表示で、操作する部分が少ない | 静的な HTML に、操作する部分だけを hydrate する | HTML とスクリプトは静的アセット |
| 操作が中心のアプリ | CSR | 殻は静的アセット、データは API |

表のほかに、次も方式の選択に入れる。

- 検索エンジンに載せるページは、HTML に中身が入る方式にする。CSR は crawler に中身が見えるかを確かめる手間が要る
- hydrate は INP を悪くする。ページ全体を hydrate せず、操作する部分だけにする
- SSR の結果を Cache API や CDN のキャッシュに置いても、Workers ではリクエストのたびに Worker が動く。キャッシュは D1 や外部 API の呼び出しを減らすだけで、Worker の起動数は減らさない
- 閲覧者ごとに変わる中身を、閲覧者をまたいで共有されるキャッシュに置かない

### 静的に配られているかを確かめる

作ったあとに、実物で確かめる。HTML が返ることだけでは、静的に配られているとは言えない。

- ビルド出力に、そのページの HTML がファイルとして入っている
- 配る側に Worker のスクリプトが無い。あっても、そのページのパスで Worker が先に動かない
- 本番でページを開いても、Worker の起動数が増えない。GraphQL Analytics API で確かめる

## 公開サイトの費用は使用量で増やさない

- 外部公開するサイトの配信に、使用量で課金される仕組みを使わない。「無料枠に収まる」は理由にしない。アクセスが急に増えれば、無料枠は超える
- R2 の読み出しや Worker のリクエストのように上限なく増えうる経路を、公開サイトの主な経路にしない。ファイル数の上限に当たるなら、画像をまとめるなどして静的アセットに収める
- Cloudflare の単価と暴走の歯止めは cloudflare-caution に従う

### 課金される経路を見つける

公開ページを開いたときに出るリクエストを、HTML、スクリプト、画像、フォント、API の呼び出しまですべて挙げる。それぞれを、静的アセットか、使用量で課金される経路（Worker、R2、D1、KV など）かに分ける。課金される経路は、「方式を選ぶ」で Worker が動く方式になった部分だけにする。
