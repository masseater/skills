# project-checklist

新しいプロジェクトの始めと大きな変更の前に、設計をユーザーが過去に下した判断と突き合わせるための一覧である。

- 設計を決める前に、各項目を設計の実物（構成、`alchemy.run.ts`、ワークフロー）と照らす

## この skill が必要な理由と達成したい状態

この skill が必要な理由は、設計の判断が、それを決めたセッションにしか残らないことにある。新しいプロジェクトを始める AI は、テンプレートの既定の形と一般的な作り方から設計する。テンプレートの Web アプリはリクエストごとに SSR する Worker なので、公開ページもそのまま SSR で作られる。ユーザーが前に「公開ページは静的に」と決めていても、その判断は今のセッションに無い。しかもこうした誤りは動いて見え、テストも verify も通るので、ユーザーが気づくまで残る。こうして同じ誤りがプロジェクトごとに作られ、ユーザーは毎回同じ指摘をすることになる。

この skill で達成したい状態は、ユーザーが一度下した設計の判断が、どのプロジェクトでも最初の設計から守られていることである。

## 公開ページは静的アセットで配る

誰にでも見せ、リクエストごとに中身が変わらないページは、Worker のコードを持たない静的アセットとして配る。プリレンダーした HTML でも、Worker の SSR を通して返すなら静的ではない。静的アセットは Worker を起動しないので、アクセスがいくら増えても費用が増えない。

- 見本は masseater/typescript-template の `apps/lp` で、作り方はそのリポジトリの AGENTS.md の「公開の静的ページ」にある。同じ形で作る
- CSP の nonce やテンプレートの既定の形は、静的にしない理由にならない

### 静的か動的かを決める

設計のときに、ページごとに次の順で決める。

1. そのページの HTML の中身を決めている入力を挙げる
2. 入力がビルド時に決まるものだけなら、静的にする。リポジトリのファイルや、ビルド時に取ってくるデータがこれにあたる
3. Cookie、ログイン状態、閲覧者ごとのデータ、リクエストごとに変わる検索条件を使うなら、動的にする
4. star の数のように時間で変わっても全員に同じものは、ページを静的にして、その部分だけを API で取る

### 静的に配られているかを確かめる

作ったあとに、実物で確かめる。HTML が返ることだけでは、静的に配られているとは言えない。

- ビルド出力に、そのページの HTML がファイルとして入っている
- 配る側に Worker のスクリプトが無い。あっても、そのページのパスで Worker が先に動かない
- 本番でページを開いても、Worker の起動数が増えない。GraphQL Analytics API で確かめる

## 公開サイトの費用は使用量で増やさない

- 外部公開するサイトの配信に、使用量で課金される仕組みを使わない。「無料枠に収まる」は理由にしない。アクセスが急に増えれば、無料枠は超える
- R2 の読み出しや Worker のリクエストのように上限なく増えうる経路を、公開サイトの主な経路にしない。ファイル数の上限に当たるなら、画像をまとめるなどして静的アセットに収める
- Cloudflare の単価と暴走の歯止めは cloudflare-caution に従う

### 課金される経路を見つける

公開ページを開いたときに出るリクエストを、HTML、スクリプト、画像、フォント、API の呼び出しまですべて挙げる。それぞれを、静的アセットか、使用量で課金される経路（Worker、R2、D1、KV など）かに分ける。課金される経路は、「静的か動的かを決める」で動的になった部分だけにする。
