# 目的と理由の記述

そうする目的を書く。目的があれば、読者は想定外の状況でも基準を当てはめて判断できる。仕様やコードを見ればすぐ分かる動作の説明は、理由の代わりにならない。

今の状態から理由を逆算してもよいが、推測であることを明示し、最終的に人間と合意を取る。

「A する必要があるため B している」の A が技術的な要素なら、その技術を採用した理由がさらに手前にあり、それが抜けている。技術用語で理由が完結するときは、ビジネスやプロダクトの要件に届くまで遡る。遡っても根拠が見つからなければ、その選択自体がオーバーエンジニアリングではないかを疑う。

```
SSR を行うためにこの設定を有効にしている。
```

設定が SSR のためであることは 1 分調べれば分かり、SSR が必要な理由が抜けている。理由があれば、実現方法の中から目的に合うものを選べる。

```
SEO のために SSR を行う必要がある。
```

良く見えるが、なぜ SEO を考慮するのかが抜けている。

```
本プロダクトは BtoC サービスである。単純なマーケティング流入のほか検索流入も期待したい。そのため SEO を考慮する必要があるので、SSR を行う。
```

要件の背景まで論理立てて含んでいるが、冗長である。プロダクトレベルの要件を各所に書くと既存の情報と重複するので、大原則の置き場所が明確ならそこは省き、正本を 1 か所に保つ。

```
検索結果から商品ページへ流入できるよう、クローラーが初回応答から主要な商品情報を取得できる必要がある。この要件を満たすため、商品ページはサーバー側で描画する。
```

「検索エンジンからの流入を期待する」はプロダクトの要件であり、技術から逆算されたものではないので、理由の着地点になる。その要件自体の理由はビジネス上のもので、技術的要件と密接に結び付けるべきではないため省いてよい。
