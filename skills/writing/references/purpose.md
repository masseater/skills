# 目的と理由

何かを決める文を書くときは目的を先に置き理由を書く。読み手が評価する順番はまず「その目的は要るのか」、次に「手段はそれに合っているか」だからである。理由が書いてあれば想定外の状況が来ても読み手は基準を当てはめて自分で判断できる。

## 理由を書く

- 仕様やコードを見ればすぐ分かる動作の説明は、理由の代わりにしない
- 理由が技術用語で終わっているときは、ビジネスやプロダクトの要件に届くまで遡る
- 今の状態から理由を逆算したときは、推測だと明示して、人間の合意を得る

「A する必要があるため B している」の A が技術的な要素なら、その技術を採用した理由がさらに手前にある。遡っても根拠が見つからなければその選択自体がオーバーエンジニアリングではないかを疑う。

```
SSR を行うためにこの設定を有効にしている。
```

設定が SSR のためだということは、少し調べれば分かる。ここで抜けているのは SSR が必要な理由である。理由があれば実現方法の中から目的に合うものを選べる。

```
SEO のために SSR を行う必要がある。
```

良く見えるがなぜ SEO を考慮するのかが抜けている。

```
本プロダクトは BtoC サービスである。単純なマーケティング流入のほか検索流入も期待したい。そのため SEO を考慮する必要があるので、SSR を行う。
```

要件の背景まで含んでいるが冗長である。プロダクトレベルの要件を各所に書くと既存の情報と重複する。置き場所が決まっている情報は各所では省き、正本を 1 か所に保つ。

```
検索結果から商品ページへ流入できるよう、クローラーが初回応答から主要な商品情報を取得できる必要がある。この要件を満たすため、商品ページはサーバー側で描画する。
```

「検索エンジンからの流入を期待する」はプロダクトの要件で、技術から逆算されたものではない。だから理由の着地点になる。その要件自体の理由はビジネス上のもので技術的要件と結び付けるべきではないため省いてよい。

## 目的を先に置く

A が手段で B が目的なら、「B のため A する」と書く。

- 目的を先に、手段を後に置く
- 目的を括弧に入れない
- 直前の文で目的が共有済みなら、繰り返さなくてよい

語順が評価の順を決める。「A する（B のため）」と書くと読み手は A が決まったものとして受け取り、B の必要性を検討する前に、A の実行方法の評価へ入ってしまう。

目的を先に置けば、「B が不要なら A も不要」「B が必要でも A が最適とは限らない」という順で評価できる。不要な目的のために手段を磨き続けたり、既存の手段を前提に目的を正当化したりすることを防げる。

```
商品ページをサーバー側で描画する（検索エンジンからの流入を得るため）。
→ 検索エンジンから商品ページへの流入を得るため、商品ページをサーバー側で描画する。
```

元の文では描画方法が先に確定し目的が後から付け足されている。直した文では検索流入の必要性を先に評価し必要ならサーバー側描画が適切かを評価できる。

括弧は本文から取り除いても判断に影響しない補足にだけ使う。目的は手段を採用する根拠でいちばん重要な情報だから括弧に入れず本文の因果関係として書く。

省略の基準は省略しても読み手が目的を認識したまま手段を評価できるかどうかである。
